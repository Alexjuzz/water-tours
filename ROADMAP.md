# Water Tours — план до первого запуска

Дата: 6 сентября 2026. Цель: первая рабочая версия за две недели, при участии владельца 1–2 часа в день (14–28 часов). Это ориентир; после первого этапа уточняем объём по результатам запуска и тестов.

Этот файл — основной порядок работ. TASKS.md содержит прежние технические заметки: его отметки и предложения необходимо сверять с кодом. Наличие реализации не означает, что сценарий проверен.

## Первая версия

- WordPress: описание прогулок, тарифы, форма покупки и получение билета.
- Spring: заказы, оплата, выпуск PDF с QR, отправка по почте, проверка и погашение сотрудником.
- Билет действует три дня, без привязки к рейсу и бронирования мест.
- Подтверждено владельцем: однократный проход, срок ровно 72 часа с подтверждённой оплаты; точная дата окончания должна быть показана клиенту. Срок настраивается для новых билетов.
- ЮKassa — основной кандидат, поскольку интеграция уже есть. Выбор аналога нужен только при препятствиях подключению.
- Почта Яндекса — доставка билетов.
- Telegram — после устойчивой основной покупки; первоначально уведомления, без отдельной логики заказов.
- PostgreSQL хранит заказы, платежи и билеты; Redis используется для временных операций. WordPress требует собственной совместимой БД — учесть её при размещении.
- Одно Spring-приложение; усложнение архитектуры не входит в первую версию.

## Исходное состояние

На момент проверки GitHub main: aae27e8. Локальный main: 71456e3, рабочее дерево чистое. Локально есть дополнительные изменения, включая OrderExpirationJob и Actuator. Перед работой повторно сверить версии: они могут измениться.

По исходникам уже существуют создание платежа ЮKassa, запрос статуса у провайдера, заказы, токены доступа, PDF/QR, выпуск и погашение билетов, SMTP. Сквозной запуск и тесты в рамках составления плана не выполнялись.

В панели Timeweb обнаружены домен water-tours.ru и включённый сервер: 1 CPU, 1 ГБ RAM, 15 ГБ NVMe, Ubuntu 20.04. В списке адресов только IPv6; панель указывает закрытые SMTP-порты 465/587. Доступ по SSH, содержимое сервера, DNS и фактическая отправка почты ещё не проверены. Ресурсы и тариф без отдельного решения не меняем.

## Правила выполнения

1. Выполняем этапы последовательно. Следующая задача — первая незавершённая в текущем этапе.
2. Одна небольшая задача — одно понятное изменение и отдельный коммит. Не смешиваем посторонний рефакторинг.
3. Перед изменениями проверяем ветку и незакоммиченные правки. Не перезаписываем работу владельца.
4. Для кода используем рабочую ветку; после проверки переносим изменения в main. Не переписываем историю.
5. Задача получает [x] только после выполнения критерия готовности. Рядом записываем коммит и результат проверки.
6. Codex выполняет и проверяет работу; Claude Code можно подключать к ограниченным задачам или независимому ревью. Два исполнителя не меняют одновременно одни файлы. Учитываем лимиты обоих инструментов.
7. Секреты остаются в переменных окружения/локальном хранилище; в Git только примеры без значений. Логи не должны содержать пароли, токены доступа и лишние данные покупателей.
8. Тесты оплаты используют тестовый магазин/имитацию API, почта — тестовый адрес или локальный приёмник.
9. Покупки ресурсов, реальные денежные операции и изменения публичного размещения выполняем после конкретного решения владельца.
10. После этапа: кратко фиксируем результат, что проверено и что осталось.
