# Water Tours

Spring Boot 3.5.6 / Java 21. Основной план работ: [ROADMAP.md](ROADMAP.md).

## Проверка проекта

Требуются JDK 21 и запущенный Docker Desktop с Linux-контейнерами.
Из папки проекта в PowerShell:

```powershell
.\mvnw.cmd -B verify
```

Первый запуск скачивает зависимости и образы. Тест автоматически создаёт отдельные
PostgreSQL и Redis на случайных портах и удаляет контейнеры после проверки.
Рабочая БД, SMTP и платёжный API не используются. Проверяется запуск Spring,
создание таблицы orders и запись/чтение Redis. Это не проверка покупки целиком.
Без Docker проверка завершается ошибкой, а не пропускается.
Testcontainers 1.21.4 выбран для совместимости с Docker 29.

## Локальный запуск приложения

1. Запустить PostgreSQL и Redis: `docker compose up -d`.
2. Скопировать `.env.example` в `.env` в корне этого репозитория и заполнить локальными
   значениями. Для БД использовать значения из compose.yml. Для платежей — тестовый магазин.
3. Запустить:

```powershell
.\mvnw.cmd spring-boot:run '-Dspring-boot.run.arguments=--spring.config.import=file:./.env[.properties]'
```

Здесь файл загружается явно как Java properties: значения без кавычек и без `export`.
Само наличие dotenv-java в pom.xml не загружает файл автоматически.
Для файла вне репозитория предпочтительно задать переменные окружения в конфигурации
запуска IntelliJ; не переносить секреты в исходники. При запуске через IntelliJ можно
также указать тот же `--spring.config.import=file:./.env[.properties]` в Program arguments,
с рабочей папкой в корне репозитория.

Сервер: http://localhost:8080. Состояние: /actuator/health.
Текущий compose.yml — для локальной разработки, не для публичного сервера.
Hibernate пока использует ddl-auto=update; миграции и production-настройки — отдельный этап.
Не запускать тестовые эксперименты на базе с реальными заказами.

## Тестирование без аккаунта ЮKassa

`mvnw.cmd -B verify` включает проверки с MockRestServiceServer: обращения платёжного
HTTP-клиента перехватываются в памяти и не отправляются провайдеру. Проверены создание
платежа с серверной суммой, отказ доверять статусу webhook при pending у провайдера и
последовательный повтор подтверждения. Это не тестовый магазин ЮKassa и не подтверждение
готовности интеграции к реальным платежам. Обычный запуск приложения по-прежнему использует
API ЮKassa; отдельного демонстрационного режима оплаты в интерфейсе пока нет.

POST /api/v1/orders/{orderId}/pay и POST /api/v1/orders/{orderId}/tickets/issue теперь требуют
параметр accessToken, полученный при создании заказа. Отсутствующий токен даёт 400, чужой — 403.
Форму WordPress нужно адаптировать при интеграции. API погашения требует роли STAFF и CSRF-токена
сессии. Бизнес-проверки временных границ и параллельного погашения выполняются следующим этапом.

## Восстановление платежей

Для нового заказа сохраняются одна попытка оплаты, её UUID и исходный JSON до вызова API.
Повтор использует тот же Idempotence-Key и неизменное тело; известная ссылка возвращается повторно.
Если ответ потерян, повтор или фоновая сверка восстанавливает ту же попытку. HTTP-запросы выполняются
вне транзакции БД. Параллельные операции блокируют одну строку заказа при изменении состояния.

Фоновая сверка включена по умолчанию, каждые 60 секунд обрабатывает до 50 ожидающих платежей.
Для полностью изолированного теста её можно отключить: payments.reconciliation.enabled=false.
Платёж со статусом succeeded принимается только после проверки id, суммы RUB, metadata и paid/captured_at.
Оплата, подтверждённая после EXPIRED, переводит заказ в PAID. Отмена не откатывает уже подтверждённый платёж.
При временной ошибке webhook возвращает 503, чтобы провайдер мог повторить доставку.

ЮKassa гарантирует идемпотентность POST только 24 часа. Мы прекращаем автоматическое повторное
создание после 23 часов от сохранения попытки: неизвестный providerPaymentId требует ручной сверки,
новый ключ автоматически не создаётся. Повторная оплата отменённого заказа в этой версии не реализована.
Старые записи без request_body/next_check_at и несколько платежей на один заказ требуют отдельной
сверки перед размещением. Не запускать новую версию на рабочей БД без резервной копии и миграций.
Новые поля payment: request_body, confirmation_url, next_check_at; сейчас схему обновляет dev Hibernate.

Контракт провайдера: https://yookassa.ru/developers/using-api/interaction-format
Уведомления: https://yookassa.ru/developers/using-api/webhooks

## Автоматические билеты и письма

Правило подтверждено владельцем: один проход, срок 72 часа с подтверждённой оплаты.
`tickets.validity: 72h` меняет срок только для новых билетов; уже выпущенные сохраняют свои даты.
Начало допустимо включительно, окончание исключительно: в точный момент validTo билет уже недействителен.

Оплаченные заказы без tickets_issued_at образуют устойчивую очередь выдачи в PostgreSQL.
TicketIssuanceJob проверяет их каждые 30 секунд; повтор и параллельный запуск не выпускают дубли.
Задержка выпуска не продлевает срок: validFrom и purchaseDate берутся из paid_at.
Погашение выполняется под блокировкой строки билета; допустим только статус ISSUED.

Заказы с выпущенными билетами и пустым tickets_emailed_at образуют очередь писем.
После успешной отправки выставляется отметка, после ошибки заказ остаётся в очереди.
Автоматическая доставка выключена: tickets.email-delivery.enabled=false.
Включать её после настройки и проверки Яндекс SMTP; интервал по умолчанию 60 секунд.
SMTP ограничен таймаутами 5 секунд. Отправка удерживает блокировку заказа; это простая схема
для небольшого объёма, при росте нагрузки потребуется отдельная таблица заданий с арендой обработки.
При неопределённом результате SMTP (сервер принял письмо, но ответ потерян) возможна повторная доставка.
Автоматическая отправка уже отмеченного письма повторно не выполняется; ручная повторная доставка — отдельная задача.

В тестах почта и PDF для сценария очереди имитируются: реальных писем нет и внешний вид PDF этим не проверен.
