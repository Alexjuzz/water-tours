# Runbook ротации секретов (задача 6.5)

Это план действий. Реальная ротация (смена паролей/ключей, SSH/firewall, действия у провайдеров) выполняется владельцем отдельно — здесь не запускается.

Общий порядок для каждого секрета: 1) убедиться, что есть путь восстановления доступа (владелец не остаётся заблокирован), 2) создать/получить новое значение у потребителя/провайдера, 3) обновить `.env` на сервере, 4) перезапустить только затронутый сервис, 5) проверить доступ новым значением, 6) отозвать старое значение у провайдера.

## DB_USERNAME / DB_PASSWORD
1. Создать нового пользователя PostgreSQL с тем же правами (не удалять старого сразу).
2. Обновить `DB_USERNAME`/`DB_PASSWORD` в `.env` на сервере.
3. `docker compose up -d water-tours` (перезапуск только приложения, PostgreSQL не трогаем).
4. Проверить health-check (`/actuator/health`) и одну тестовую операцию чтения.
5. Отозвать/удалить старого пользователя PostgreSQL.

## MAIL_USERNAME / MAIL_PASSWORD
1. Доставка писем сейчас выключена (`tickets.email-delivery.enabled=false`) — низкий риск, можно менять в любой момент.
2. Обновить в `.env`, перезапустить приложение.
3. Перед включением доставки — контрольное письмо по отдельному разрешению (см. TASKS.md, задача 4).

## YOOKASSA_SHOP_ID / YOOKASSA_SECRET_KEY
1. **Учесть активные заказы**: перед сменой убедиться, что нет заказов в `PENDING_PAYMENT`, ожидающих webhook по старому ключу (или согласовать с ЮKassa переходный период).
2. Получить новый ключ в личном кабинете ЮKassa (владелец).
3. Обновить `.env`, перезапустить приложение.
4. Проверить тестовым платежом в режиме, не создающим реальную оплату.
5. Отозвать старый ключ в личном кабинете ЮKassa.

## TELEGRAM_BOT_TOKEN
1. Оповестить получателей о временной недоступности бота (если сценарий подключён и включён).
2. Получить новый токен через @BotFather.
3. Обновить `.env`, перезапустить приложение — `TelegramPollingJob` переподключится.
4. Отозвать старый токен через @BotFather (revoke).

## STAFF_PASSWORD
1. Убедиться, что владелец имеет доступ к серверу (SSH) для правки `.env` — это единственный путь восстановления для встроенного аккаунта.
2. Сгенерировать новый пароль, обновить `.env`.
3. Перезапустить приложение — старые сессии/remember-me cookie не аннулируются сами по себе, поэтому сменить и `STAFF_REMEMBER_ME_KEY` одновременно, если требуется принудительный logout всех устройств.
4. Проверить вход новым паролем.

## STAFF_REMEMBER_ME_KEY
1. Смена аннулирует все текущие remember-me cookie (пользователям потребуется войти по паролю снова) — предупредить владельца перед сменой.
2. Обновить `.env`, перезапустить приложение.

## SSH-ключ на боевой сервер / firewall
Не входит в эту задачу — правки SSH/firewall провайдера выполняются владельцем отдельно, без участия приложения.

## Восстановление доступа владельца
Единственный staff-аккаунт хранится как переменные окружения на сервере — восстановление доступа = SSH на сервер (владелец) → правка `.env` → перезапуск контейнера. Нет отдельного email/SMS-сброса пароля, потому что аккаунт один и управляется владельцем инфраструктуры напрямую; отдельный self-service сброс пароля добавлять не стали — избыточно для одного встроенного аккаунта и добавил бы канал для новых атак (fишинг сброса, перехват письма).
