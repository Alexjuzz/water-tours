# Disaster recovery

Полностью автономный docker-compose стек: Postgres, Redis, backend-приложение,
MariaDB, WordPress, Nginx. Поднимает копию сайта с нуля на любой машине с Docker
и восстанавливает данные из бэкапа.

Когда использовать: сервер на Timeweb недоступен/потерян/удалён, нужно поднять
сайт заново — на новом сервере, локально или где угодно ещё.

## Что нужно заранее

1. **Docker** установлен на машине, где разворачиваем.
2. **Этот репозиторий** (`git clone`) — тема/плагин WordPress берутся отсюда
   (`integrations/wordpress/`), не из бэкапа.
3. **Бэкап** — папка с тремя файлами: `appdb.sql`, `wordpress-db.sql`,
   `wp-content.tar.gz`. Берётся либо с сервера (`/root/backups/daily/<дата>/`),
   либо с этого компьютера (`D:\WATER_BACKUP\daily\<дата>\`), если сервер
   недоступен.

## Шаги

```bash
cd ops/disaster-recovery
cp .env.example .env
# впишите в .env: STAFF_PASSWORD, STAFF_REMEMBER_ME_KEY, WORDPRESS_DB_ROOT_PASSWORD,
# WORDPRESS_DB_PASSWORD (новые значения — это не обязательно старые секреты),
# и по желанию TELEGRAM_*/YOOKASSA_*/MAIL_* если они уже есть.

./restore.sh /путь/к/бэкапу/20260907-091959 http://localhost
```

Второй аргумент — адрес, по которому сайт будет доступен после восстановления
(например `https://water-tours.ru`, если поднимаете на новом сервере с тем же
доменом, или `http://localhost`, если проверяете локально). Скрипт пропишет
его в WordPress автоматически.

Скрипт сам:
1. Собирает и поднимает все контейнеры (пустые базы).
2. Ждёт, пока Postgres и MariaDB станут healthy.
3. Восстанавливает базу приложения (заказы/билеты/платежи) из `appdb.sql`.
4. Восстанавливает базу WordPress из `wordpress-db.sql`.
5. Копирует `wp-content/uploads` из бэкапа (тема и плагин берутся из git, не
   из бэкапа — так они всегда актуальны).
6. Прописывает адрес сайта в WordPress.
7. Перезапускает backend.

## После восстановления

- Сайт: адрес, который вы указали вторым аргументом.
- Персонал: `<адрес>/login`, логин/пароль из `.env` этой папки.
- Проверьте `/actuator/health` — приложение должно быть живым (может быть
  `DOWN`, если SMTP недоступен — это ожидаемо, не блокер).
- Если это новый домен — понадобится: обновить DNS, выпустить SSL (например
  `certbot` перед этим Nginx или заменить на реверс-прокси с TLS), проверить
  Telegram-бот (`TELEGRAM_BOT_TOKEN`/`TELEGRAM_BOT_USERNAME` в `.env`), и
  реальные ключи ЮKassa/SMTP, если они уже были получены.

## Ограничения (сознательно не упаковано)

- **Без TLS "из коробки"** — Nginx в этом стеке отдаёт только HTTP. На новом
  домене TLS настраивается отдельно (Let's Encrypt/certbot или внешний прокси),
  так как зависит от актуального состояния DNS в момент восстановления.
- **Секреты не восстанавливаются автоматически** — `.env` в этой папке
  заполняется вручную. Реальные `TELEGRAM_BOT_TOKEN`/`YOOKASSA_*`/`MAIL_*`
  нигде не бэкапятся (это сознательное решение — они не должны лежать в файлах
  бэкапа), их нужно взять из вашего менеджера паролей / прежнего `.env` сервера.
- **Порты БД смотрят только на 127.0.0.1** (`5439`, `6379`) — так же, как в
  проде; если поднимаете стек как реально публичный сервер, добавьте свой
  Nginx/TLS перед портом 80, как было настроено на Timeweb.
